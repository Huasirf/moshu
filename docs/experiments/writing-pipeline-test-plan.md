# 墨枢写作流水线 · 实机验证方案（v2 最终版）

> 目的：以「模拟真实用户点击」的方式，用上传的《种族大逃杀，从获得S级技能开始》（1135 章 / 约 41 万字）做拆书原料，跑通「拆书 → 立项 → 素材 → 大纲 → 生文 → 去味 → 审稿 → 定稿写回 → 一致性」全链路，产出 30 章可读初稿，并逐环节给出可判定的有效性结论。
>
> 模型：**Gemini（gemini-4-argon-medium，中转 https://uuapi.io）为全链路主力**，已于 2026-10-22 由用户实测「测试连接」通过并设为默认生成模型；DeepSeek 仅作限流/失败时的兜底；bge-m3 本地向量不变。
>
> 分工：AI 负责所有文本生成；我负责界面操作、流程推进、过程记录与**文本验收**（不代写正文）。
>
> 本方案只定义流程与判定口径。执行中若发现需要改数据契约、改表、改提示词体系或改架构，一律停下、出决策请求包、咨询强模型后再动。

## 1. 目标与边界

### 1.1 要回答的问题

| 编号 | 问题 | 判定方式 |
|---|---|---|
| Q1 | 拆书 AI 是否按提示词完成任务 | 产物字段完整率、角色卡数量、专有名词污染率、大纲可支撑度 |
| Q2 | 新设定能否被 AI 正确写入素材库并可读回 | 资产 8 类筛选/详情、Agent `read_assets`/`read_character_state` 回读一致 |
| Q3 | 大纲提示词是否生效、是否够详细、能否指导生文 | 30 章齐全率、字段长度、资产引用覆盖、单章目标字数、写稿日志 |
| Q4 | 正文能否达到真人作者水平（AI 味控制） | 高危词密度、句长方差、对话比，与**原书人类样本**同口径对比 |
| Q5 | 去味是否真的改写句式/语气，而非删词 | 去味前后文本差异度 + 事实一致性（剧情不被改坏） |
| Q6 | 审稿能否自动对照数据库发现设定错误 | 预埋 3 类错误，检查 findings 是否命中且带证据 |
| Q7 | 定稿是否自动写回现状/道具/关系 | `attribute_values`、`canon_item_events`、`entity_relations`、阶段流水线 |
| Q8 | 向量检索、跨章一致性、素材库参考是否有效 | 10 条检索命中率、每 5 章一致性抽查、重复段落检测 |

### 1.2 明确不做

- 不复用原书人名、地名、势力名、专有名词、关系网、地图、具体技能名。
- 不追求与原书相似度；只复用「升级节奏 / 爽点类型 / 章节钩子结构」这类抽象层。
- 不绕过界面直接写数据库（观测脚本只读，不改数据）。
- 不为了跑通而临时放宽校验（闸门、事务、阶段守卫）。

## 2. 拆书样本裁剪（控制成本的关键）

原书文件共 1135 条章节标题，但**只有第 1–118 章与第 636–654 章真正带正文**，其余 1000+ 章只有标题行（首次按 89 章抽样时，第 51 章起每章仅 50 余字，已作废重做）。

**取样原则**：前 50 章整段保留（看开局、金手指觉醒、爽点密度演进）；中后段取其唯一一段完整正文（第 636–654 章，看后期境界、势力结构与钩子密度）。合计 **69 章、约 18.7 万字**。

| 区段 | 原章号 | 章数 | 取样理由 |
|---|---|---|---|
| 开局 | 第 1–50 章 | 50 | 黄金三章、能力验证、第一次组队与打脸、早期节奏基线 |
| 中后 | 第 636–654 章 | 19 | 后期境界、势力博弈与钩子密度 |

- 样本文件：`F:\MoShu_e2e\samples\breakdown-sample.txt`（保留原标题，导入时平台按顺序重编号为 1–69）。
- 预计拆书阶段模型调用 ≈ 70 次（1 次全局推演 + 69 次逐章蓝图），向量化走本地 bge-m3。

> 说明：跨区段拼接会让参考项目的章节连续性失真，但参考项目只用于「提炼模式」，不用于写作连续性验证，这是可接受的取舍。

## 3. 执行纪律（模拟用户）

1. 所有业务操作走界面：欢迎页、侧栏、对话框、草稿编辑器、批量生成面板；不调用 `ipc` 直接写库。
2. 允许的"非界面"动作只有三类：只读观测（查库、统计文本、截图）、备份、生成测试样本。
3. 每次操作记录：入口路径 → 参数 → 实际日志 → 产物 → 结论（通过/不通过/阻塞）。
4. 出现阻断：先判断是否属于 §8 的停手条件；属于就停，不属于则记录后继续。
5. 每阶段结束做三件事：备份项目库、更新测试记录表、向我汇报一页结论。

### E1 拆书（平台导入工作流）

**操作**：欢迎页 →「导入小说」→ 选择 `breakdown-sample.txt` → 等待自动拆章预览（应显示 69 章）→ 项目名 `参考·种族大逃杀` → 保存路径 `F:\MoShu_e2e\projects\ref-breakdown` → 开始导入（步进模式）。

**观察点**

1. 导入初始化：69 章正文写入 + 69 章向量化，知识库计数是否 = 69。
2. 全局推演：向量采样 4 类各命中几条；`novelConfig` 9 个字段是否齐全；`architectureFiles` 4 份文本是否非空。
3. 分层确认弹窗（DR-06）：世界观 / 人物 / 关系是否出现、内容是否可读、跳过与应用的差异。
4. 逐章蓝图：69 条是否全部落库，失败是否可重试；Gemini 的 JSON 稳定度（R3）在此首次计量。

**Q1 判定**

| 指标 | 通过线 |
|---|---|
| 角色卡数量 | 3–8 人，含主角/反派 |
| 空字段 | `novelConfig` 必填项空值 ≤ 1 |
| "（待确认）"占比 | ≤ 30% |
| 专有名词污染 | 原书人名/地名出现在新书设定中 = 0 |
| 蓝图覆盖 | 69/69，且每条有 purpose + keyEvents + suspenseHook |
| JSON 解析失败率 | ≤ 5%（失败条目可重试） |

**产物**：参考项目、拆书原始输出（复制到 `F:\MoShu_e2e\records\E1-breakdown.json`）。

| 指标 | 通过线 |

### E5 黄金三章（逐章精写）

每章固定流程（全程界面操作）：

```
章节卡「写这一章」→ 生成草稿 → 保存
→ AI 修稿（可选 1 次）→ 去 AI 味（确认强度与前后对照）
→ AI 审稿 → 审稿台账逐条处理（修复/忽略）
→ 定稿（warning 显式豁免）→ 观察后处理日志与写回结果
```

每章记录：字数、生成耗时、去味前后 diff 摘要、审稿 findings 数（按严重度）、写回条数、阶段流转。

**Q4/Q5 判定（与原书人类样本同口径）**

| 指标 | 目标 |
|---|---|
| 单章字数 | 1800–2300 |
| 高危 AI 词密度（不由得/仿佛/似乎/空气凝固/嘴角勾起…） | 去味后 ≤ 原书人类样本的 1.5 倍 |
| 句长标准差 | 去味后上升（句式不再整齐划一） |
| 对话占比 | 25%–40% |
| 章末钩子 | 与蓝图 suspenseHook 语义一致，且为未解问题 |
| 剧情事实 | 去味前后关键事件、人物、道具无变化（审稿复核） |
| 开篇 | 首段 300 字内出现具体危机或异象，不写天气/回忆 |

三章后再做一次「读者视角」通读：若仍有明显 AI 腔，先调风格档案的规则与强度（平台能力），仍不行再讨论提示词改造（属停手条件 S2）。

## 6. 新书创作提案（需你确认或替换）

**书名**：《潮渊纪·读名者》
**一句话**：潮水每七日上涨一次，吞没低地；拾荒少年墨砚从父亲留下的断名刀里读到死者的"残名"，靠重铸别人废弃的权能一步步向上。

**背景**：大陆被"潮渊"周期性淹没，人类住在浮屿与高地；文明以"真名"立身——每人一生可在名骨上刻一个真名，真名决定可调用的权能。势力：镇渊司（官方秩序）、渡潮商会（资源与航运）、拾荒团（底层）、渊裔（被潮渊改造的类人）。

**核心天赋「读名 / 铸名」**
- 读取真名残片 → 获得一次性权能（每用一次衰减），并读取原主一段记忆碎片。
- 代价：每读一枚，主角遗忘自己的一段记忆（记忆账本），越强越"薄"。
- 升级链：读一枚 → 并行三枚 → 拼伪名（可持续权能）→ 铸名于人（共享）→ 改命（改写规则）。
- 爽点来源：一次性权能的奇招、记忆碎片揭秘、越级反杀、身份反转。

**等级体系**：凡名（刻名一至三重）→ 真名（铸名）→ 铭域 → 载道 → 改命。

**初始角色**：墨砚（主角，孤儿，被拾荒团老渡捡回养大，师徒/监护关系，不写父子情）、老渡（退役巡渊人，引路人）、沈青棠（商会二小姐，利益盟友/女主候选）、贺沉（巡渊使，第一个压迫者）、阿箬（失名少女，长线伏笔/女主候选）。

**主角动机（不走父子线）**：墨砚生来"无名"——名骨上没有任何字，被判为无法刻名的无名者，只能捡别人的残名活着。他要查清的不是父亲下落，而是**自己的名字为什么被抹掉**。

**女主策略**：单女主或多女主在 E2 拆书结论后决定，E4 大纲前锁定；感情线服务主线，不写父辈恩怨与家族伦理。

**初始道具**：断名刀（半截，可暂存 1 枚残名）、潮痕尺（测权能等级）、三枚残名（第 1 章所得）。

**黄金三章节拍**
| 章 | 目标 | 阻碍 | 收益 | 章末钩子 |
|---|---|---|---|---|
| 1 | 潮涨前夜在淹没区拾荒换钱 | 渊裔围猎，濒死 | 断名刀吸入残名，觉醒读名 | 刀里的残名在喊一个被"削名"的婴儿 |
| 2 | 混过渡潮船盘查，带阿箬上船 | 盘查 + 第一次付代价 | 残名"折光"救场，获得船票 | 巡渊使贺沉注意到"无名者" |
| 3 | 在船上立足 | 贺沉当面追查 | 第二枚残名越级伤敌后脱身 | 记忆碎片里出现镇渊司的"削名刑"刀法 |

**三卷结构（30 章）**
- 卷一 拾荒者（1–10）：觉醒 → 立足 → 第一次越级 → 卷末被商会盯上。
- 卷二 渡潮船（11–20）：势力博弈 → 队友 → 背刺 → 卷末船沉，阿箬失名真相。
- 卷三 镇渊司（21–30）：自己"无名"的线索 → 削名刑黑幕 → 卷末反转（他的名是被人生生刮掉的，动手者就在镇渊司高层）。

> 需要你确认：题材方向、主角天赋的"遗忘代价"是否接受（它会让爽感带痛感），以及 30 章是否就写到这里收束。

## 7. 写作风格基线（写进风格档案，作为 Q4 判定依据）

- 第三人称限知，单章 1 个 POV，不越界写他人内心。
- 开篇不写天气、不写回忆；第一句给动作或异象。
- 单段 ≤ 4 行；长短句交替；每章 ≥ 2 处具体感官细节（触/嗅/听）。
- 对话占比 25%–40%，对话带动作，不写"他说道"连排。
- 禁用/降频词：不由得、不禁、仿佛、似乎、空气仿佛凝固、嘴角勾起、眼神复杂、深吸一口气、缓缓、微微、瞬间、顿时、命运的齿轮…
- 章末必须是"未解决的威胁 / 未兑现的收益 / 未回答的问题"。

### 7.1 文本验收评分卡（我的验收职责）

每章生成并定稿后，我按五维打分（1–5），并记录客观指标：

| 维度 | 5 分标准 | 3 分（及格线） |
|---|---|---|
| 开篇抓力 | 首段即危机/异象，读者无跳读冲动 | 前 3 段能进入情境 |
| 场景具体度 | 有可触摸的物件、气味、动作，不靠抽象形容词 | 有场景但偏概述 |
| 人物声口 | 对话有身份差异，去掉名字仍能分辨谁在说 | 对话基本合理但同质 |
| 节奏与爽点 | 每章有目标-阻碍-收益-钩子，爽点兑现不拖延 | 有事件但收益偏弱 |
| 语言自然度 | 无成串套话，句长错落，情绪靠动作与细节 | 偶有 AI 腔但可读 |

**通过线**：五维总分 ≥ 18/25，且「语言自然度」≥ 4，且无阻断级设定错误。

**分档**：A（可直接发布，只需轻度润色）/ B（可读，少量 AI 腔，需人工润色）/ C（明显 AI 味，需重写）。
**要求**：黄金三章 ≥ B+（四项 ≥ 4 分），30 章平均 ≥ B；出现 C 档的章节必须重写并记录原因。

**客观指标（与原书人类章节同口径）**：字数 1800–2300、高危词密度、句长标准差、对话占比 25%–40%、段长分布、相邻章 8-gram 重合率。

**去味有效性盲测**：每章把「去味前 / 去味后」随机顺序交给我盲判哪版更像人写，命中率 ≥ 70% 才算去味有效。

## 8. 停手条件与专家咨询

出现以下任一情况：**停止执行 → 写决策请求包（背景/已核实事实/约束/候选方案/待决问题/期望输出）→ 咨询强模型 → 登记 DR → 再动手**。

| 编号 | 情况 | 典型表现 |
|---|---|---|
| S1 | 数据层/契约问题 | 写回不落库、读不回、阶段卡死、事务失败 |
| S2 | 提示词结构性失效 | 字段缺失率 > 20%、连续多章不按节奏、去味规则完全不命中 |
| S3 | 成本或时长失控 | 单章调用 > 预算 2 倍、批量长时间无进展 |
| S4 | 需要架构改动 | 需新增表/列/工具/流程，或改现有契约 |
| S5 | 关键能力缺失 | 如属 F1（属性定义无入口）、F2（关系图谱无数据源）导致无法验收 |

**已预判的两处摩擦**

- **F1 属性定义**：现状面板依赖 `attribute_defs`，当前没有界面入口创建。若 E3 无法填充，按 S5 处理（候选：项目创建时播种默认定义 / Agent 工具支持 / 设置页入口）。
- **F2 关系图谱**：定稿写回按 DR-08 只写显式结构化关系，抽取结果若无结构化关系则图谱为空。若 E7 仍为空，先确认是否为设计预期，再决定是否补抽取（属 S4）。

**Gemini 通道的两处协议风险（观察项，不预先改代码）**

- **R3 JSON 稳定性**：GeminiProvider 忽略 `response_format`，拆书/大纲/写回抽取全靠提示词约束 + 解析容错。E1 统计解析失败率，> 5% 时按 S2 评估是否需要补 `responseMimeType`。
- **R4 多段输出**：正文只取 `parts[0].text`。若模型返回多段（含思考段/分段），会出现正文被截断或混入思考内容；黄金三章逐章检查，命中即按 S1 停手。

## 9. 备份与改动规范

1. 执行前：`git diff` 存 patch；`git rev-parse HEAD` 记录；备份 `~/.vela` 两个配置。
2. 每个阶段结束：把项目 `.vela\*.db` 复制到 `F:\MoShu_e2e\backups\<阶段>\`。
3. 任何代码改动前：再存一次 patch；改动后必须过 `typecheck / lint / test / vite build`。
4. 跑 `vitest` 前若应用刚启动过，先 `pnpm rebuild better-sqlite3` 切回 Node ABI；跑应用前再切回 Electron ABI（启动器会自动处理）。
5. 不在未备份时执行数据库迁移或批量删改。
