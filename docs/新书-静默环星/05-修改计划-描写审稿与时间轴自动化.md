## 二、感官描写合理性审稿（N1）

### 2.1 两个实锤样本

| 位置 | 原文 | 问题 | 改法 |
|---|---|---|---|
| 第 3 章落地段 | 「掌心按在一圈略微凹陷的地面上，**触手粗糙**，还带着点尚未散尽的余温」 | 「触手」是名词（触须、章鱼触手），读者第一反应是手变成了触手；作者想写的是「触感」 | 「触感粗糙」或「掌心下的地面粗糙」 |
| 第 2 章走廊段 | 「空气里混着浓郁的**汗酸味与臭氧味**」 | 汗酸味有来源（人群）；臭氧味在场景里找不到来源，普通读者也不知道臭氧是什么味，只会读成堆词 | 改为「汗酸味、电机过热的橡胶味」；若保留臭氧，前一句必须给出电弧 / 高压设备放电 |

两处都不是文笔问题，是**信息不成立**：读者会在脑子里追问「哪来的」。审稿必须能抓住。

### 2.2 S-1 词形误用（error）

**规则**：写感官时只能用感受名词（触感、手感、气味、声音、温度），不能用身体部位或物体名词顶替。

- 词表：`触手`、`触须`、`肢感`、`视力感` 等；出现即高亮。
- 判定：`error`。歧义词会直接改变读者脑内画面，不能放行。
- 修法：`触感 / 手感 / 掌心下的触感`。
- 例外：真写触手生物时可用，但必须同段有「触手」本体（章鱼、怪物肢体）。

### 2.3 S-2 气味 / 声音 / 触感必须有来源（error）

每个感官描写过三问：

1. **谁产生的**？（人、机器、伤口、火、霉、化学品）
2. **在不在当前场景**？来源必须在同段或前一段出现，不能靠读者脑补。
3. **读者凭常识认不认得**？只有专业读者能认的气味，不进正文。

| 类型 | 可直接写（常识有来源） | 必须补来源（高危词） |
|---|---|---|
| 气味 | 汗、铁锈、机油、焦糊、霉、灰尘、消毒水、烟、食物、腐烂 | 臭氧、硫磺、氨、甲醛、乙醚、麝香、硝烟、血腥 |
| 声音 | 电流声、金属摩擦、风声、水声、脚步、呼吸 | 次声波、高频啸叫、等离子嗡鸣 |
| 触感 | 粗糙、湿冷、黏、烫、震、麻 | 微电流刺痛、空间扭曲感 |

判定：

- 找不到来源 → `error`。
- 来源在上一章 / 远处，本章只剩气味 → `warning`，要求补一句来源。
- 反例：臭氧味无电弧、血腥味无伤口或尸体、焦糊味无热源。

### 2.4 S-3 感官堆叠（warning）

- 同一段超过 2 种感官，且不推动情节 → `warning`。
- 连续 3 段用气味 / 触感开头 → `warning`。
- 无功能触感（台面凉、指尖划过桌面、灰尘在光里飘）→ `warning`，建议删。

### 2.5 落点

1. `writing_style` 增补 4 条（见附录 A 的 27–30 条）。
2. `consistency_check` 模板新增输出维度 `sensory_issues`：

```json
{
  "sensory_issues": [
    {
      "type": "word_misuse | no_source | stacked | no_function",
      "severity": "error | warning",
      "quote": "触手粗糙",
      "reason": "触手是名词，读者会误读为触须",
      "fix": "触感粗糙"
    }
  ]
}
```

3. `rule_items` 新增两条 hard：
   - `R-13-1 感官来源`：气味、声音、触感必须有场景内来源，高危词必须同段交代产生者。
   - `R-13-2 感官词形`：不得用身体部位 / 物体名词顶替感受名词。
4. 审稿报告新增类别：`描写合理性 · S-1/S-2/S-3`。

## 三、时间校准审核（N2）

### 3.1 现有数据前提

| 表 | 现有字段 | 问题 |
|---|---|---|
| `project_timeline_config` | calendar / era_start / time_flow / notes | 只有全局设定，没有每章时间 |
| `blueprint_timeline_events` | story_time / absolute_time / duration / location / participants / summary | 计划层可用，`absolute_time` 已是「第N天」口径 |
| `canon_timeline_events` | chapter_number / sequence / characters / location / time_flow / summary / impact | **没有时间字段**，定稿抽取的时间无处落，也无法比对 |

结论：先补字段（N4），再做校准（N2）；否则「时间校准」只能靠模型空对空。

### 3.2 时间表达式识别

| 类型 | 例子 | 归一化 | 置信度 |
|---|---|---|---|
| 绝对日期 | 6 月 30 日、试炼纪年 100 年 | `offset_day`（以 `era_start` 为第 1 天） | 高 |
| 场内天数 | 第 1 天、场内第 3 天、首试第 12 天 | `offset_day`（场内单独加前缀） | 高 |
| 相对时间 | 三天后、次日、当晚、半小时后 | 上一事件 + 增量 | 高 |
| 时段 | 清晨 / 上午 / 正午 / 下午 / 入夜 / 深夜 | 06 / 09 / 12 / 15 / 19 / 23 时 | 中 |
| 持续时长 | 待了三天、两个时辰、半日 | `duration_min` | 中 |
| 模糊时间 | 几天后、没多久、过了好一阵 | 区间 2–5 天 / 1–3 小时 | 低，不自动写 |
| 并行 | 与此同时、同一时间、另一边 | `parallel` | 中 |

解析器要求：

- 中文数词（一二三……十、半、两、几）必须能转数值。
- 每月固定 30 天，不设星期；跨月按 30 天进制累加。
- 场内 / 场外分开记：场内 4 天 = 场外 1 天，禁止混算成一条轴。

### 3.3 判定流程

```
① 抽取    正文 → 时间候选句（LLM + 正则双路）
② 归一    候选句 → {offset_day, clock, duration_min, confidence, evidence}
③ 匹配    与已存事件比对：同章 sequence / 章号+地点+参与者+事件关键词
④ 校验    单调性、范围、时长一致、硬约束
⑤ 判定    pass / warning / error，写台账
```

### 3.4 决策矩阵（核心）

| 情形 | 条件 | 判定 | 动作 |
|---|---|---|---|
| **新增节点**（时间轴上没有） | 不早于上一章末事件；不晚于下一章计划首事件；与文中明示时长一致；通过硬约束 | `pass` | 放行，可自动写入时间轴 |
| 新增节点 | 早于上一章末，且未标「回忆 / 倒叙」 | `error` | 阻断；改正文或补闪回标记 |
| 新增节点 | 与前后间隔矛盾（正文写「三天后」，轴上是 6 天） | `error` | 列差异，要求二选一修正 |
| 新增节点 | 超前于全书当前进度 / 未来章计划 | `error` | 阻断，防止提前发生 |
| 新增节点 | 超出单场时长、月配额、私路冷却等硬约束 | `error` | 阻断 |
| 新增节点 | 只有模糊词（几天后 / 没多久） | `warning` | 标 `confidence=low`，不自动写入 |
| **已有节点**（时间轴上能匹配到） | 日期一致；钟点差 ≤ 30 分钟；时长差 ≤ 20% | `pass` | 判为同一事件，合并，不重复写 |
| 已有节点 | 日期一致，钟点或时长超容差 | `warning` | 列 diff（轴上 X，正文 Y），人工确认 |
| 已有节点 | 日期不一致 | `error` | 阻断，按定稿正文或时间轴二者之一修正 |
| 回忆 / 倒叙 | 明确标注「回忆 / 倒叙 / 那年」 | `pass` | 入轴但 `time_flow=flashback`，不参与前后章单调性 |
| 回忆 / 倒叙 | 未标注且时间倒流 | `warning` | 提示补标注，不直接判 error |

一句话口径：**没有重复且合理就放行；有重复就看一致；新增就看范围。**

### 3.5 容差表

| 项 | 容差 | 说明 |
|---|---|---|
| 日期 / 第 N 天 | 0 | 必须精确，不允许「大概同一天」 |
| 钟点 | ±30 分钟 | 深夜跨日按场景判断，不粗暴取整 |
| 持续时长 | ±20%，或 ±10 分钟，取较大值 | 「半日」按 4 小时 |
| 模糊词 | 区间内 | 只提示，不自动写 |
| 跨章间隔 | ≥ 0 | 且必须与「三天后 / 次日」等明示一致 |

### 3.6 硬约束引用

时间校准必须同时核对以下已锁规则：

1. 场内 : 场外 = 4 : 1。
2. 公共试炼标准 7 天；首试封闭场 12 天。
3. 月配额个人 2 次 + 团队 1 次，每月 1 日 00:00 重置。
4. 私路冷却 28 天，返回当日起算。
5. 每月 30 天，不设星期。
6. 回归只回原点，落地 30 秒防护圈；首试由系统回收。
7. 成年礼窗口：生日后 30 天内。

## 四、定稿后自动写入时间轴（N3 + N4 + N5）

### 4.1 现有链路

`finalize-chapter.command.ts` 的 `buildFinalizePostProcessSteps` 已有：

| 步骤 key | 内容 | 是否含时间 |
|---|---|---|
| `kb_import` | 正文入库 | 否 |
| `chapter_notes` | 本章要点提取 | 否 |
| `kb_summary_import` | 摘要索引 | 否 |
| `canon_writeback` | 事件 / 角色 / 事实 / 剧情线写回 | **否**（`TimelineEvent` 只有 summary / location / time_flow） |
| `arc_summary` | 卷摘要 | 否 |

`canonStore.writeback` 是单事务、按章 clear + insert，适合扩展，不需要另起一套写入。

### 4.2 新步骤 `timeline_extract`

- 位置：`canon_writeback` 之后、`arc_summary` 之前。
- `critical: false`，失败不阻塞定稿。
- 输入：定稿正文、本章蓝图、`project_timeline_config`、前 12 章 `canon_timeline_events`、本章 `blueprint_timeline_events`。
- 模型：新增模板 `extract_chapter_timeline`，强 JSON、低温度（0.1）。
- 输出：§3.7 的 `events` + `time_issues`。
- 校验：直接复用 `time-calibrator`，**不另写一套判定**。

### 4.3 三级写入门槛

| 校准结果 | 写入 | 台账 | 注入 |
|---|---|---|---|
| 全部 `pass` | 写 `canon_timeline_events`，`status='confirmed'`，`source='finalize_extract'` | `info` | 参与「前情时间线」 |
| 存在 `warning` | 写 `status='pending'`，不覆盖旧事件 | `warning` + 待确认列表 | 不参与前情，只在审稿参考里标「待确认」 |
| 存在 `error` | 不写；候选存 `status='rejected'` 或只留台账 | `error` | 不参与注入；提示先修正文 |

> 用户口径落实：**没有重复 + 时间合理 + 不冲突 → 放行；已有时间点 → 比对一致性；新增节点 → 检查合理范围。**

### 4.4 幂等与覆盖规则

1. 重新定稿同一章：先删该章 `source='finalize_extract'` 的事件，再写；`source='manual'` 的手工事件不动。
2. 同章重复执行不产生重复行（沿用 `canon_timeline_events(chapter_number, sequence)` 唯一索引）。
3. 正文改动导致时间变化：先比对旧事件，生成 diff 记录，再覆盖已抽取事件。
4. 手工在时间线面板改过的事件锁 `locked=1`，自动抽取不得覆盖，只提示冲突。

### 4.5 v6 → v7 迁移

```sql
ALTER TABLE canon_timeline_events ADD COLUMN absolute_time TEXT NOT NULL DEFAULT '';
ALTER TABLE canon_timeline_events ADD COLUMN duration TEXT NOT NULL DEFAULT '';
ALTER TABLE canon_timeline_events ADD COLUMN source TEXT NOT NULL DEFAULT 'canon';
ALTER TABLE canon_timeline_events ADD COLUMN confidence REAL NOT NULL DEFAULT 1.0;
ALTER TABLE canon_timeline_events ADD COLUMN evidence TEXT NOT NULL DEFAULT '';
ALTER TABLE canon_timeline_events ADD COLUMN status TEXT NOT NULL DEFAULT 'confirmed';

ALTER TABLE blueprint_timeline_events ADD COLUMN locked INTEGER NOT NULL DEFAULT 0;
ALTER TABLE blueprint_timeline_events ADD COLUMN lock_source TEXT NOT NULL DEFAULT '';
```

- 旧数据回填：`absolute_time` 留空、`status='confirmed'`、`source='canon'`；**不猜测旧事件时间**。
- `TimelineEvent` 类型同步补 `absoluteTime / duration / source / confidence / evidence / status`。

### 4.6 UI（TimelineView）

1. 每条事件显示：时间（第 N 天 / 钟点）、地点、参与者、来源徽标（计划 / 定稿抽取 / 手动）、置信度。
2. 新增「待确认」区：显示 `pending` 事件与差异（轴上 vs 正文），提供「确认 / 驳回 / 改时间」。
3. 时间轴按 `absolute_time` 排序；空时间排末尾并置灰，标「未定时间」。
4. 确认后写 `status='confirmed'`，重新计算前情注入。

### 4.7 日志与可观测

- `⏳ [时间轴] 抽取 N 条：自动写入 A / 待确认 B / 冲突 C`
- `⏳ [时间轴] 与第 X 章冲突：正文「三天后」= 第 6 天，轴上为第 9 天`
- 每次 LLM 调用的 `contextPack.stats` 记录时间线槽位字数。

### 4.8 注入口径

- `db:timeline-context` 的「前情时间线」只取 `status='confirmed'`。
- `pending` 只在审稿参考块中出现，标注「待确认，不得当作既成事实」。
- `timeline_canon` 槽位同样过滤 `pending / rejected`。

### 6.2 验收

- 定稿第 3 章后，`canon_timeline_events` 出现 1–2 条事件，`absolute_time='1'`、`status='confirmed'`、`source='finalize_extract'`。
- 重新定稿同章：不新增重复行；`source='manual'` 事件保留。
- 正文写「三天后」而轴上差 6 天：产出 `duplicate_drift` 或 `new_node_conflict` 的 `warning/error` + diff。

## 附录 A：对话排版软规则 10 条（整理版，待落 `writing_style`）

1. 对话独立成段，不跟在叙述句后面。
2. 不用冒号引出对话；引号前不加「他说 / 他问」。
3. 引号内一句一段；超过 68 字（手机横屏约 4 行）拆成两次说，中间插动作或停顿。
4. 连续纯对话不超过 3 段（原著分布：1 段 62.9%、2 段 15.8%、3 段 9.6%）。
5. 纯对话段均长 14–20 字，单段不超过 42 字（原著 P90）。
6. 每 2–3 段对话插入一个动作 / 环境 / 心理落点，防止「空中对话」。
7. 说话人标识靠动作、称呼、语气，不靠「XX 说」。
8. 排比句一句一段。
9. 单段不超过 4 行；超过 5 行拆段。
10. 段落之间空一行；面板段、引号段、叙述段三者不混排。

## 附录 B：人物面板书写标准（待落 `writing_style`）

1. 面板独立成块，一字段一行，整块前后空行。
2. 全角冒号 + 阿拉伯数字；附加信息用括号。
3. 字段顺序：力量 → 敏捷 → 体魄 → 心识 → 等阶 → 装备 → 技能 → 道具卡 → 心域容量 → 特殊饰品 → 凭证。
4. 只放数据，不写情绪、形容词、叙述句。
5. 每章不超过 2 次；数值变动时只写变动行。
6. 禁止句中零散词条（如「视野角落里的【节点·未勘测】」）；禁止用叙述替代面板。
7. 任务面板单独成块：任务名 / 进度 / 时限 / 状态。
