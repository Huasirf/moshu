# 墨枢 MoShu 平台大更新 · 调查结论与实施计划

> 版本 v1｜范围：UI 易用性、设定/规则保存与注入、AI 审稿合规校验、Vela→MoShu 品牌与目录迁移
> 基线：当前工作区 f:\MoShu（git 分支有未提交改动，见文末风险控制）

## 已确认决策（2026-10-30）

1. **改名**：全改名 + 自动迁移（D1+D2+D3 全做），复制不移动、保留旧目录可回退。
2. **规则区**：结构化条目库（`rule_items` + 稳定编号 R-x-y），`project_core.rulebook` 降级为编译产物。
3. **审稿触发**：生成完成后自动跑「轻量档」（程序化数值闸 + hard 规则逐条勾选），硬违规提示后由用户确认修复；完整档保留手动入口。
4. **视觉**：由我生成 3–4 套墨枢图标与开屏候选，用户选定后替换 `build/icon.*` 与开屏。
5. **时间线**：新增「章纲时间线管理器」模块，章纲设计时同步录入事件次序与具体时间，落库后供 Gemini 检索参考；与已定稿 Canon 时间线做漂移校验。
6. **参考入口**：生成 / 审稿 / 改稿 / 章纲 / 时间线五条链路统一走 `ContextPack` 槽位装配，规则、世界观、时间线、Canon 都给 Gemini 明确入口，并在界面显示"本次注入了什么"。

### 2. 按钮与控件尺寸

| 现状 | 位置 |
|---|---|
| 基础 `Button` 尺寸：sm 24px / default 28px / lg 32px / icon 28px，字号统一 12px | src/components/ui/Button.tsx:L11、L28-L33 |

### 3. 世界观 / 规则区 / 大纲的保存与注入（重点）

实测当前项目数据库（`F:\MSnovel\开局误入高阶试炼\.vela\vela.db`，只读查询）：

| 字段 | 字符数 | 说明 |
|---|---|---|
| rulebook | **9175** | 规则区，已接近/超过注入上限 |
| world_setting | 11387 | 含 16 张关卡卡，有固定小节标题 |
| core_outline | 730 | 核心大纲（偏短，蓝图另有 30 章） |
| premise / worldbuilding / characters_arch / synopsis | 924 / 2772 / 1945 / 1314 | 架构四大件 |
| canon_items | 140 行 | 资产库 |
| blueprints | 30 行 | 章纲 |

关键代码事实：

1. **规则区有硬截断，且现在已经在截断。** `truncateRulebook` 上限 9000 字（src/services/prompts/prompt-builder.ts:L88-L93），当前规则 9175 字 → 每次生成/审稿都有约 175 字（末尾「返界锚 / 灰舟」两条）看不到。规则继续增加，丢失比例会线性上升，且**没有任何提示**（只在 prompt 尾部加一句"请精简规则区"，模型不会因此回头）。
2. **规则区是无标题的平铺编号列表**（120 行全部以 `1.` `2.` 开头，6 组之间仅空行分隔）。→ 无法像世界观那样按标题切片，只能整份塞或整份截，这是"遵守率不可控"的结构性根因。
3. **世界观是切片注入，规则区是全文注入。** 生成时 `buildWorldSettingSlice` 按固定标题抽取（总览/颜色表/等级/闯入/命中关卡卡/生成规则），预算 12000 字（src/services/prompts/world-setting-slice.ts:L104-L151，调用点 generate-draft.command.ts:L147-L158）。规则区走 `withRulebook` 全文（同处 L158、L281）。
4. **审稿时世界观并未真正注入。** `review-chapter.command.ts:L153` 只注入 `rulebook`；世界观走 Canon 的 `worldbuilding`（L119-L140），而 `worldBuilding` 槽位在 Canon 构造成功时被替换成一行"见上方正史摘要与规则区"（L100）。→ 审稿员看不到关卡卡字段、奖励上限、准入表这些结构化设定，只能靠 Canon 摘要推断。
5. **保存是手动整存，无版本、无字数与冲突提示。** `NovelConfigEditor` 里规则区/世界观/大纲都是一个大 `Textarea`（L354-L386），点「保存」才写库（L161-L165 → `saveProject`）。规则区无自动保存、无历史版本、无超限预警、无重复/矛盾检测。
6. 生成侧 token 预算 28000 tokens（generate-draft.command.ts:L256-L263），超预算只打警告不裁剪，规则区一旦放大就会挤压章纲与 Canon。

### 4. AI 审稿

| 现状 | 位置 |
|---|---|
| 本地规则审稿：禁用词、视角越界、道具未持有、地点冲突、时间倒流（硬编码 5 类） | src/services/review/rule-review.ts:L1-L18、L142-L299 |
| LLM 审稿模板 `consistency_check`：10 个检查维度，已含「设定规则合规 / 试炼设计合规 / 术语与境界命名」 | src/services/prompt-templates.ts:L1526-L1595 |
| 审稿上下文：Canon + 最近 2 章摘要 + 伏笔，**无世界观切片** | src/services/workflows/commands/review-chapter.command.ts:L101-L156 |
| 结果落 `review_findings`，按草稿版本过滤展示 | finding-mapper.ts、finding-scope.ts、ReviewFindingsPanel.tsx:L52-L76 |

结论：审稿模板"看起来"覆盖规则合规，但（a）规则被截断、（b）规则是长文本没有编号无法定位、（c）世界观硬事实未注入、（d）没有"逐条规则打勾"的机制、（e）生成完不会自动触发。所以实际遵守率取决于模型心情，你的 10 条硬规则（1/4 铁律、装备门槛、奖励上限、配额、术语）没有一条被程序化校验。

## 第二部分 设计方案

### 方案 A｜UI 易用性

**A1. 统一控件尺寸（一次改，全站生效）**

- 在 src/index.css 增设密度 token：`--ctrl-h-sm:32px`、`--ctrl-h-md:36px`、`--ctrl-h-lg:44px`、`--ctrl-font:13px`；`--radius-md` 保持。
- `Button` 尺寸改为 sm 32 / default 36 / lg 44 / icon 36，字号 12→13，横向 padding +2；`IconBtn`、`Input`、`Textarea`、`NativeSelect`、`Switch` 同步（全部走同一 token，禁止各写各的 px）。
- 322 处手写 `<button>` 分两批替换：**第一批**（用户高频页面）DraftEditor、ChapterCardEditor、EditorArea、NovelConfigEditor、SettingsModal、CharacterEditor、StoryRehearsalDialog、BottomPanel、Sidebar 系列，统一改用 `<Button size="sm">` 或新增的 `<IconBtn>`；**第二批**（低频）随迭代逐步替换。为保留各自布局，一次性提供 `text-[13px] px-3 py-1.5` 的等价 class 映射。
- 同步放宽列表行高：文件树/章节列表行 `py-1`→`py-1.5`，Tab 高度 32→36。

**A2. 主页改为「工作台」（新建 `src/components/pages/HomeWorkspace.tsx`，替换 WelcomePage 的空白态展示）**

布局：
```
┌ 顶部：墨枢 Logo + 搜索框 + [新建项目][导入小说][打开文件夹] （大按钮 h-44）
├ 我的项目（列表/卡片 切换 · 排序：最近打开 / 名称 / 进度）
│  ┌ 项目卡：封面/首字色块 · 项目名 · 题材+章节数 · 进度条(已定稿/总章) · 最后打开时间
│  │ 操作：打开（单击卡即开）· 更多（定位 / 重命名 / 移除 / 删除）
│  └ 网格视图最多 3 列，列表视图显示更多列（路径、总字数、最后修改）
└ 空状态：一张引导卡 + 大号「新建项目」按钮
```

数据层：
- 主进程新增项目登记表 `~/.moshu/projects.json`（结构：`{ id, name, path, genre, totalChapters, draftedCount, wordCount, lastOpenedAt, pinned, coverColor, missing }`），在 `project:open` / 保存 / 定稿时增量刷新（打开时读一次该项目 db 的 `project_core` + `chapter_pipeline` 统计，成本可接受）。
- 新增 IPC：`project:registry-list`、`project:pin`、`project:forget`（与现有 `project:recent-*` 并存，逐步替换）。
- 打开失败（路径不存在/非墨枢项目）在卡片上标灰并给「重新定位」按钮，避免"点了没反应"。
- 保留 `ProjectManagerDialog` 作为精简版入口，内部复用同一数据源，不再维护第二套列表逻辑；侧边栏 HomeSidebarPanel 只保留 5 条 + 「全部项目」跳工作台。

### 方案 B｜设定 / 规则「保存 + 注入」重构（核心）

**B1. 存储：规则区从"一坨文本"升级为"结构化条目库"**

新增表（迁移在 electron/database.ts）：

```
rule_items(
  id TEXT PK, project_id, code TEXT,        -- 如 R-2-3，稳定编号，正文/审稿都引用
  group TEXT,                                -- 等阶 / 试炼卡 / 场次 / 结算 / 心域技能装备 / 装备门槛 / 准入特权
  title TEXT, body TEXT,                     -- 一行摘要 + 完整条目
  severity TEXT,                             -- hard(不可违背) / soft(建议)
  tags TEXT,                                 -- JSON：[属性, 门槛, 1/4铁律, 返界锚...]
  active INTEGER, sort INTEGER, updated_at
)
rule_snapshots(id, project_id, hash, chars, items_count, content, created_at)  -- 保存即快照，可回滚
```

- `project_core.rulebook` 保留为"编译产物"（由 rule_items 按 sort 拼出，正文注入与旧逻辑兼容）；编辑入口改为条目编辑，旧库首次打开时自动解析现有 rulebook（按空行分组 + 编号）生成条目，**零手工迁移**。
- 保存行为：条目级即时保存（失焦/命令+S），另加"整份快照"（每次保存生成 hash，超 30 份清理最旧）；界面显示「字数 / 条目数 / 快照历史」并可一键回滚。
- 校验与预警（编辑器侧，不阻塞保存）：字数超 8000 提示"规则已超出单次注入预算，将按相关度注入"；重复条目（标题相似度 > 0.85）提示合并；数值冲突检测（门槛表 F/E/D 与装备门槛表、奖励上限表抽出数字后互比，冲突标红）。

**B2. 注入：从"全文/截断"改为"分层 + 相关度 + 显式未注入清单"**

新增 `src/services/prompts/rulebook-slice.ts`（与 world-setting-slice 同构）：

| 层 | 内容 | 预算 | 何时注入 |
|---|---|---|---|
| L1 硬规则摘要 | 所有 `severity=hard` 条目的 code + title 一行 | ≤ 2500 字 | 生成 / 审稿 / 改稿 / 蓝图 全部注入 |
| L2 本章相关规则全文 | 按 tags 与本章（关卡卡命中、场景 props、蓝图关键词）匹配，含命中的关卡卡数值 | ≤ 5000 字 | 生成 / 改稿 |
| L3 未注入清单 | 剩余条目只列 `code + title`，并注明"未展开，如需判定先查规则区" | ≤ 1200 字 | 生成 |

- 取消 9000 硬截断，改为"预算感知"：在 28000 token 预算内给规则固定配额（约 8000 字），超出按相关度排序；prompt 里明确写「以下规则编号未展开：R-x-x…」，让模型知道边界而不是无知觉地裁掉。
- 规则编号写进正文生成模板的系统约束（"涉及判定时必须按 R-x 条目口径"），但不要求正文出现编号（避免破坏文风）。
- 世界观保持现有切片机制，只做两点增强：(1) 关卡卡不在本章时，卡内"准入/奖励/失败条件"三项仍给 1 行摘要（当前是整卡不带）；(2) 切片预算从 12000 提到 12000（不变）但在日志里输出实际注入的卡号与省略卡号。

**B3. 保存层的 UI 体验**

- `NovelConfigEditor` 拆为三个独立编辑器入口（世界观 / 规则区 / 核心大纲），不再挤在一个长 Textarea：
  - 世界观：按 `## / ###` 折叠的分节编辑器，关卡卡单独卡片化（字段表单：颜色档次/类型/地图/核心目标/失败条件/关键机制/奖励/死亡处理），保存时回写 world_setting 的 fix 标题格式（保证切片器始终命中）。
  - 规则区：分组 + 条目（见 B1）。
  - 核心大纲：保留文本，但增加"卷/章锚点"目录树侧栏与字数统计。
- 三处都加：自动保存（debounce 800ms）+ "已保存/未保存"状态点 + 保存前校验摘要（字数、条目数、异常项）。

### 方案 C｜AI 审稿增强：每章完工即做世界观 / 规则合规校验

**C1. 新增"规则合规专审"（`src/services/review/rule-compliance.ts`）**

- 输入：rule_items（hard 全量 + 本章相关 soft）、worldSetting 切片（含命中关卡卡）、蓝图场景 props（数值）、Canon 快照（N-1 章状态）。
- 分两步：
  1. **程序化数值闸**（零成本）：从正文抽取数字与单位，对照规则表校验——属性增长是否只在结算/属性卡/天材地宝后、单次增量是否超该场颜色上限（白4/黄8/蓝15/红20/紫25/金50/黑100）、装备门槛表（F/E/D 50/300/700；C/B/A/S 1300/2500/3600/5000）、1/4 铁律、配额次数、携带槽位件数、时间流速（内 4:1）。命中 → `error`，附规则编号与原文句子。
  2. **LLM 逐条勾选**：把规则按 group 分批（每批 ≤ 20 条），要求输出 `{rule_code, verdict: pass|violation|n/a, quote, reason}`；只对 `violation` 生成 finding，`n/a` 不落库。世界观维度同样按关卡卡字段逐项核对（地图类型/核心目标/失败条件/奖励档）。
- 与现有审稿合并：`review-chapter.command` 在本地规则审稿之后、LLM 一致性审稿之前插入本步骤；finding 增加 `ruleCode` 字段，台账去重时同 `ruleCode + quote` 视为一条。

**C2. 触发时机（"每章写完自动跑"）**

在 `generate-draft.command` 生成完成、Canon Gate 通过后追加一步可配置的 `POST_GENERATE_AUDIT`：
- 默认开启「轻量档」：程序化数值闸 + 规则合规专审（仅 hard 规则），不调全量一致性审稿（省 token）。
- 可选「完整档」：再跑一次 `consistency_check` 全维度审稿。
- 结果写入 `review_findings`，并在章节 Tab 顶部显示合规徽章：`规则 0 冲突 / 世界观 0 冲突`（点击打开右侧 findings 面板）。
- 若出现 `hard` 违规 → 生成结束提示"本章有 N 条硬规则冲突，是否按规则修复"，调用现有 `RefineFromReviewCommand`（扩展参数传 rule_code 上下文），不自动改稿（避免越权）。

**C3. 审稿界面改造**

- `ReviewFindingsPanel`：按「规则编号 / 世界观 / 术语 / 文风」分组；支持筛选 severity；每条显示 `R-2-3` 徽标，点击跳到规则区对应条目（`NovelConfigEditor` 定位高亮）。
- `ReviewReport`：新增"规则合规矩阵"区块（规则 code × pass/violation/n-a 一览），让每章的合规状态一目了然。
- 章阶段增加 `audited`（在 `drafted → reviewed` 之间），用于批次流程"仅审稿"和"审稿+修复"的区分。

### 方案 E｜章纲时间线管理器（新增模块）

**调查结论**

| 现状 | 位置 |
|---|---|
| `canon_timeline_events` 表已存在（chapter_number + sequence + time_flow + summary + impact），但**只由定稿后的 Canon 抽取填充**，是"已经发生"的时间线 | electron/database.ts:L682-L694、canon-repository.ts:L209-L241 |
| 注入侧只取最近 10 章、渲染上限 6000 字，闪回单独列出 | context-builder.ts:L95-L133 |
| 已有 `TimelineView.tsx` 视图，但只读，只展示 Canon 已发生事件，不能编辑 | src/components/editor/TimelineView.tsx、timeline-view.ts |
| **章纲本身没有时间字段**：`BlueprintScene` 只有 title/summary/goal/conflict/turn/words/props/characters，`blueprints` 无任何时间列 | blueprint-repository.ts:L11-L49 |
| 蓝图编辑 `ChapterCardEditor` 无法录入"第几日/几点/持续多久/是否闪回" | src/components/editor/ChapterCardEditor.tsx |

→ 结论：计划层（章纲）没有任何时间数据，"设计时就排好时间"这件事目前无处可放；Canon 时间线是事后产物，Gemini 写章时看不到"本章应该发生在什么时候、距离上一章过了多久"。

**E1. 数据模型（计划层，与 Canon 层分开，互不覆盖）**

```
blueprint_timeline_events(
  id TEXT PK, chapter_number INTEGER, sequence INTEGER,
  title TEXT,                     -- 事件名（与场景一一对应时取场景标题）
  scene_index INTEGER,            -- 关联 blueprints.scenes_json 的场景下标，-1 表示章级事件
  occur_offset_day REAL,          -- 距项目时间原点的天数（可为小数，0.5=半天）
  occur_clock TEXT,               -- '06:40'，可空（只知日期不知时刻时留空）
  duration_min REAL,              -- 持续分钟，可空
  location TEXT, characters TEXT, -- JSON 数组
  time_flow TEXT,                 -- sequential / flashback / parallel / ellipsis(时间跳跃)
  summary TEXT, impact TEXT,
  source TEXT,                    -- outline(章纲设计) / canon(定稿抽取) / imported
  locked INTEGER,                 -- 定稿后锁定的计划事件
  updated_at TEXT
)
project_timeline_config(
  id PK, origin_label TEXT,       -- 时间原点，如「蓝星历 2147-03-01 06:00 首试当日」
  origin_iso TEXT,                -- 可解析绝对时间，用于显示日历
  flow_ratio TEXT DEFAULT '1:1',  -- 场景内流速（试炼内 4:1 等），JSON 可多段
  updated_at
)
```

- 计划事件与 Canon 事件**同构但不共用表**：定稿后由 Canon 抽取写 `canon_timeline_events`（现状不动），同时把该章计划事件标记 `locked=1`，之后只允许在时间线模块里"改计划"并记录差异，不直接覆盖 Canon 事实。
- 章纲 -> 时间线采用**双向可追溯**：`blueprints.scenes_json` 加可选 `time` 字段（`{day, clock, durationMin, flow}`），保存章纲时同步生成/更新 `blueprint_timeline_events`（以 blueprint 为准）；在时间线模块里拖动/改时间时反写回场景 `time`。冲突以"最后编辑方"为准并弹提示，不做双向自动合并。

**E2. 录入方式（设计章纲时就顺手排时间）**

1. **场景级录入**（主入口）：`ChapterCardEditor` 每个场景行新增一行时间控件——`第 [N] 日 [HH:MM]（可空）` + `时长 [分钟]` + `[顺序/闪回/并行/跳跃]`。默认值：同章上一场景 + 预估时长（0），章首默认上一章最后事件次日 08:00。
2. **章级时间条**（章纲卡片顶部）：显示"本章时间跨度：第 12 日 06:40 → 第 14 日 21:10（约 2.6 天）"，可直接改起止。
3. **时间线模块集中编辑**（新页面）：按卷分组的横向时间轴，可增删改、拖动排序、批量"顺延 N 天""对齐到上一事件"。
4. **自动推导（可选，需确认）**：读取蓝图 `keyEvents` 里的时间词（"三天后""次日""当夜"）给出建议值，不自动写入。
5. **从 Canon 反向导入**：已有定稿章可一键把 `canon_timeline_events` 导入为计划事件（`source=canon`），补齐 1–3 章，使全书时间轴从第 1 章就连续。

**E3. 校验收紧（与方案 C 合并执行）**

- 章内倒流：`sequence` 递增但 `occur_offset_day` 递减且非闪回 -> `error`。
- 跨章倒流：第 N 章首个事件早于第 N-1 章末事件（非闪回）-> `error`。
- 角色地点冲突：同一角色在重叠时间段出现在两个地点 -> `warning`。
- 流速不符：外部经过 X 天，场内事件跨度应 ≈ X×4（试炼场）-> `warning`，引用规则编号 R-x。
- 计划/Canon 漂移：定稿后 Canon 抽取的时间与 `locked` 计划事件差异超过阈值 -> `warning`，列差异表。
- 未排时间：本章有事件但 `occur_offset_day` 空 -> `info`（提醒补全，不阻塞）。

**E4. 给 Gemini 的参考入口（时间线槽位）**

| 槽位 | 内容 | 预算 | 用于 |
|---|---|---|---|
| `timeline_chapter` | 本章计划事件全量（含时间/时长/闪回标记/地点/人物） | ≤ 1500 字 | 生成、审稿 |
| `timeline_anchor` | 前 3 章最后 2 个事件 + 全书当前日期（由 `origin + offset` 换算） | ≤ 600 字 | 生成、章纲 |
| `timeline_canon` | Canon 最近 10 章已发生事件（沿用现有渲染，6000 字上限） | ≤ 6000 字 | 生成、审稿（交叉验证） |
| `timeline_conflict` | 计划 vs Canon 的差异摘要 | ≤ 500 字 | 审稿 |

章纲生成（`refresh-blueprint` / 章纲批量）追加要求：输出 `scenes[].time = {day, clock, durationMin, flow}`，生成结束后自动写入计划时间线（`source=outline`），让"设计章纲顺便产生时间"闭环。

### 方案 F｜统一参考入口（Context Slots / ContextPack）

现状问题：五条链路（生成、审稿、改稿、章纲、时间线）各自手工拼 prompt，槽位名不一致（`withRulebook` / `withSystemRules` / `withWorldBuilding` / `withCanonContext`），有的截断有的不截，无法回答"这次 Gemini 到底看到了什么"。

**F1. 新增 `src/services/prompts/context-slots.ts`**：声明式注册所有可注入槽位。

| 槽位 key | 来源 | 预算 | 命中条件 |
|---|---|---|---|
| `rule_digest` | rule_items hard 条目（code+title） | 2500 | 全部链路 |
| `rule_scope` | rule_items 本章相关全文 | 5000 | 生成 / 改稿 |
| `rule_index` | 未展开条目 code+title | 1200 | 生成 |
| `world_slice` | worldSetting 固定标题切片 + 命中关卡卡 | 12000 | 生成 / 审稿 |
| `blueprint_scenes` | 本章蓝图场景（含 props 数值与 time） | 3000 | 生成 / 改稿 |
| `chapter_timeline` | 计划时间线 | 1500 | 生成 / 审稿 |
| `timeline_anchor` | 前情时间锚点 | 600 | 生成 / 章纲 |
| `canon_facts` / `canon_character_state` / `canon_timeline` | Canon 快照 | 现有预算 | 生成 / 审稿 / 改稿 |
| `asset_refs` | 本章引用资产（含数值与限制） | 800 | 生成 / 改稿 |
| `foreshadowing` / `previous_ending` / `rag` | 现有 | 现有 | 生成 / 审稿 |

每个槽位声明：`source(loader) / budget / priority / required / truncation`。`buildContextPack(link, chapter, options)` 按链路配置组装、按预算裁剪、输出 `{ text, stats: {slot, chars, truncated, omitted} }`。

**F2. 可观测性（这是"是否遵守"的唯一可信证据）**

- 每次生成/审稿把 `contextPack.stats` 写进工作流日志与 `llm_calls` 记录，并在 AI 输出面板顶部显示「本次参考：规则 46 条（硬 32/相关 14）、世界观 3 段 + 关卡 11、时间线 8 条、Canon 12 条、省略 9 条」。
- 生成模板尾部固定输出**参考清单回执**（不写进正文，只写进日志）：模型被要求在 JSON 尾部回显它实际用到的规则编号；缺省不改正文。
- 审计页（可后置）按章列出"注入清单 vs 违规项"，用于评估遵守率随预算变化。
